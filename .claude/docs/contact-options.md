# お問い合わせ方式の比較資料（contact-options）

- 作成日: 2026-10-27
- ステータス: **検討用（未決定）**。決定後に decisions-log へ記録し、`spec/feature/` にお問い合わせ機能の仕様を起こす。
- 関連: `.claude/docs/unotame-inventory.md`「お問い合わせ方式の候補」、D-003（静的出力）、D-006（rsync デプロイ）、D-008（ステージングなし）

---

## 1. 前提と現状

### 前提
- サイトは Astro の静的出力（`dist/`）で、Xserver に GitHub Actions + rsync で配信する（D-003 / D-006）。
- Xserver は PHP を実行できる。つまり「静的サイト＋同じサーバーの PHP 1 ファイル」という構成をとれる。
- ステージングはない（D-008）。確認はローカルで行い、本番でしか起きない差分（メール送信など）は本番切替の手順で確かめる。

### 現行 `/contact/` の実装
- `page-contact.php` はタイトル「お問い合わせ」を出したあと、`the_content()` で WordPress の固定ページ本文を表示するだけ。
- テーマ内（`functions.php` / `header.php` / `footer.php`）には、フォームや送信処理の記述がない。
- **このため、フォームは WordPress のプラグイン（Contact Form 7 など）のショートコードで本文に埋め込んでいると推測されるが、コードからは断定できない。**
  以下は WP 管理画面で確認が必要（質問 Q1）。
  - 使っているプラグインの名前と、確認画面・自動返信の有無
  - 入力項目（名前・メール・件名・本文・添付ファイルなど）
  - 通知メールの送信先と送信元（From）アドレス
  - 迷惑メール対策（reCAPTCHA など）を入れているか

## 5. 案ごとの長所・短所と注意点

### 案 1: Xserver 上の PHP スクリプト

**長所**
- 追加費用も外部サービスもいらない。契約中のサーバーだけで完結する。
- 確認画面（JS）・自動返信・デザインを完全に制御できる。
- 問い合わせ内容を第三者のサービスに預けずに済む（個人情報の説明が簡単になる）。
- 現行の WordPress もおそらく同じ Xserver からメールを送っているため、届きやすさの面で今と大きく変わらない見込み。

**短所**
- 迷惑メール対策・入力チェック・セキュリティ対策を自分で実装し、保守し続ける必要がある。
- ローカルの `npm run preview` では PHP が動かない。実際のメール送信は本番でしか確かめられない（ステージングなし）。
- Astro（TS）の中に PHP が 1 ファイルだけ混ざり、言語が 2 つになる。

**運用上の注意点**
- **メールの送り方**
  - `mb_send_mail()`（Xserver の sendmail）でも送れるが、届きやすさを考えると **SMTP AUTH（PHPMailer などで Xserver のメールアカウントから送る）** のほうが確実。
    From は自ドメインのアドレス（例: `noreply@unotame.com`）にし、問い合わせた人のアドレスは `Reply-To` に入れる（他人のアドレスを From にすると SPF / DMARC で弾かれる）。
  - Xserver 側で SPF / DKIM を設定（または有効になっていることを確認）する。DMARC も検討する。
  - Xserver の送信の目安は全プラン共通で「1 時間 1,500 通・1 日 15,000 通」。迷惑メールと判断された場合は、範囲内でも制限される（出典は 7 章）。
    個人のポートフォリオの件数なら上限は問題にならないが、**Bot に大量送信されると、自動返信を通じて自分のアカウントが迷惑メール送信元とみなされるおそれがある**。このため、自動返信を付けるなら Bot 対策は必須。
- **セキュリティ**
  - **ヘッダーインジェクション対策**: 名前・メールアドレス・件名から改行（CR/LF）を取り除くか、含まれていたら拒否する。メールアドレスは `filter_var(..., FILTER_VALIDATE_EMAIL)` で確認する。
  - **CSRF**: フォームは静的 HTML なので、サーバーで発行したトークンを埋め込む通常の方法がそのまま使えない。次のどれか（または組み合わせ）で対応する。
    1. `Origin` / `Referer` ヘッダーが `https://unotame.com` であることを確認する（いちばん簡単）
    2. 送信の直前に PHP からトークンを fetch して取得する（セッションまたは Cookie を使う double-submit）
    3. Turnstile の検証を CSRF 対策の代わりとみなす（トークンは使い捨てで、ドメインに紐づくため）
    → 問い合わせフォームではログイン状態を悪用されるリスクが小さいため、**1 と 3 の組み合わせで十分**と考える。
  - **Bot 対策**: **Cloudflare Turnstile**（無料・Google のトラッキングなし）または reCAPTCHA v3 を使い、トークンは PHP からサーバー側で検証する。あわせて honeypot（人には見えない入力欄）を置き、簡単なレート制限（IP ごとに一定時間内の送信回数を制限）も入れる。
  - Turnstile や SMTP の **秘密鍵・パスワードはリポジトリに置かない**。`public_html` の外（例: `~/unotame.com/config/contact-config.php`）に手動で一度だけ置くか、GitHub Secrets から書き出す。どちらにするかは要決定。
  - エラー時に PHP の詳細なエラーを画面に出さない（`display_errors=Off`）。応答は JSON で返し、JS で表示を切り替える。
- **rsync `--delete` との関係**
  - `contact.php` を Astro の `public/` に置けば、毎回 `dist/` と一緒に配信されるので `--delete` で消える心配はない。**ただし次のものは配信先に置くと消されるため、配信先の外に置くか `--exclude` で除外する。**
    - 秘密情報を書いた設定ファイル（上記のとおり `public_html` の外に置くのが第一）
    - レート制限用の一時ファイルやログ（`public_html` の外に置くか、`--exclude` する）
    - Xserver が自動で作るファイル（`.user.ini`、Xserver の管理画面が書き込む `.htaccess` の設定など）。`.htaccess` は Astro の `public/` に置いて管理する方針と合わせて検討する
  - 本番切替前は WordPress 本体が同じ公開ディレクトリにある。`--delete` を本番に初めて流すときの対象は、`spec/infra/hosting-and-deploy.md` の本番切替手順で扱う。
- **ローカルでの確認**
  - PHP 単体は `php -S localhost:8000` などで動かし、送信は「メールを送らずに内容をログに出す」モードで確かめる。
  - 本番では切替直後に実際に送信して確認する手順を、本番切替のチェックリストに入れる。
  - Xserver の PHP バージョンを確認し、ローカルでも同じバージョンにそろえる（要確認）。

### 案 2b: 国内フォームサービス（SSGform / formrun）

**SSGform**
- 長所: 静的サイト向け。**無料で月 100 件、自動返信あり、reCAPTCHA / Turnstile 対応**。HTML を自分で書くので、デザインの自由度は案 1 と同じ。実装は最小。
- 短所: 小規模なサービスで、運営会社や継続性は要確認（料金ページに会社名がない）。無料枠でのデータ保存・ファイル添付の仕様も要確認。
- 無料枠（確認日: 2026-10-27）: Free 0 円で月 100 件、フォーム URL は無制限。Starter 980 円/月で 1,000 件、Pro 2,980 円/月で 5,000 件。出典: https://ssgform.com/ 、https://ssgform.com/plans

**formrun**
- 長所: 国内大手で、管理画面（問い合わせの対応状況の管理）が充実している。
- 短所: 無料プランの制限が多く、自動返信は使えない。formrun のロゴが表示される可能性がある。有料プランは月額が高め。埋め込み型を使うとデザインが制約される（HTML フォーム連携なら自由度は上がる）。
- 無料枠（確認日: 2026-10-27）: FREE はフォーム 1 個、回答の受付上限は約 1,000 件、受信通知は 1 アドレス、自動返信は不可。月間の回答数の記載（約 30 件/月？）は読み取りがあいまいなため**要確認**。最安の有料プランは BEGINNER で年契約 2,980 円/月（税抜）、単月契約 3,880 円/月（税抜）。出典: https://form.run/pricing

### 案 3: Google フォーム

**長所**: 無料で、すぐに作れる。迷惑メール対策と継続性は Google に任せられる。
**短所**: 見た目をサイトに合わせられない（iframe）。外部リンクにすると、ユーザーがサイトの外に出てしまう。確認画面は作れない。ポートフォリオ（デザインの品質を見せる場）としては印象面で不利。無料版での回答数の上限は、公式の情報を確認できなかったため要確認（個人サイトの件数なら実質問題にならない見込み）。

### 案 4: サーバーレス関数 + メール API（Cloudflare Workers + Resend など）

**長所**: 自由度が高く、Turnstile との相性も良い（同じ Cloudflare）。無料枠が十分にある。PHP を混ぜずに TypeScript で統一できる。
**短所**: 構成要素が増える（Cloudflare アカウント、Workers のデプロイ、メール API、unotame.com の DNS への SPF / DKIM レコード追加）。デプロイ経路が Xserver 以外にも増える。個人サイトの規模に対しては作りすぎ。
**無料枠（確認日: 2026-10-27）**
- Cloudflare Workers Free: 10 万リクエスト/日。出典: https://developers.cloudflare.com/workers/platform/pricing/
- Resend Free: 3,000 通/月、100 通/日、ドメイン 3 個。Pro は $20/月。出典: https://resend.com/pricing
- Cloudflare Turnstile Free: 無料。ウィジェットはアカウントあたり 20 個まで、チャレンジ数は無制限。出典: https://developers.cloudflare.com/turnstile/plans/

### 案 5: メールリンク / SNS DM のみ

**長所**: 実装も保守も不要。個人情報を預かる仕組みを持たない。
**短所**: アドレスを公開すると収集され、迷惑メールが増える（難読化しても完全には防げない）。メールソフトが設定されていない環境では `mailto:` が動かない。依頼主にとって手間が増え、問い合わせの機会を逃しやすい。サイトの目的（依頼の受け口）と合いにくい。
→ 単独で使うより、フォームの補助（「SNS からでも可」など）として併用するのが現実的。

## 6. 推奨案

### 第一案: 案 1（Xserver 上の PHP。Turnstile + honeypot + SMTP 送信）
**理由**
1. **費用ゼロ・外部依存なし**で、自動返信・確認画面（JS）・デザインをすべて自分で制御できる。フォームサービスの無料枠で自動返信が使えるのは SSGform だけで、他は有料になる。
2. 問い合わせ内容を第三者のサービスに保存しないので、個人情報の説明が簡単で、サービス終了や値上げの心配がない。
3. 契約中の Xserver が PHP を使える以上、そこで完結させるのがインフラの構成として最も単純（案 4 のように配信先を増やさない）。
4. 弱点（自前の対策と、ローカルで確認しにくいこと）は、PHP を 1 ファイルの小さな範囲に抑え、「メールを送らずログに出すモード」と本番切替時の送信確認手順で補える。

**条件**: 実装コストは案 2 より大きい。P1 でここまで作りたくない場合は、次点の案で始め、P2 以降で案 1 に切り替える段階的な進め方もとれる。フォームの HTML は共通にしておけば、送信先を変えるだけで移行できる。

### 次点: 案 2b の SSGform（フォームサービス）
**理由**
1. 無料で自動返信と Turnstile / reCAPTCHA が使え、HTML を自分で書けるので、デザインと確認画面（JS）は案 1 と同じようにできる。
2. 実装が最小で、ローカルから実際に送信して確認できる（ステージングがない方針と相性が良い）。
3. 月 100 件は個人ポートフォリオには十分と見込まれる。
**懸念**: 運営の継続性とデータの保存仕様が不明なので、採用前に利用規約とプライバシーポリシーを確認する。
