# feature-spec

UNOTAME の機能仕様を、既存仕様と同じ構成で書くためのスキル。仕様は `implementer` と `tester` が
そのまま使える粒度（受け入れ条件まで）にすることが目的。

## 事前に読むもの
- `.claude/docs/unotame-inventory.md`（その機能のフェーズ・位置づけ・未決事項）
- 既存の `.claude/spec/feature/*.md`（フォーマットと用語の統一のため）
- 関連する `.claude/spec/infra/*.md`・`.claude/spec/design/*.md`
- 移行元となる現行 WP テーマの該当ファイル（例: Works 一覧なら `archive.php` と `assets/js/script.js`。退避後は `legacy/` 配下）

## 保存先と命名
- `.claude/spec/feature/<kebab-case-name>.md`（例: `works-list.md`, `cms-integration.md`）。
- 作成したら `.claude/spec/feature/README.md` の一覧と、棚卸の「仕様ファイル」列を更新する。

## テンプレート（この構成で書く）
```markdown
# 機能仕様: <日本語名>（<英名スラッグ>）

## 目的
<この機能が何のために存在するか>

## スコープ（対象フェーズ）
- <含むもの / 含まないもの（将来拡張）を明確に>

## 現行（WordPress）の振る舞い
<移行元の挙動・URL・テンプレート。該当なしなら「なし」>

## データ構造案
<TypeScript 前提の案。microCMS スキーマ・ドメイン型・props の骨子。実装での調整余地を残す>

## 振る舞い
<ページ構成・データ取得フロー・UI 挙動・URL。箇条書きで具体的に>

## 受け入れ条件
- <テストで合否判定できる粒度の条件を列挙>

## 将来拡張（任意）
<後フェーズで足す予定の要素>

## 未決事項
<決め切れていない点。まとめて提示する>
```

## 原則
- **受け入れ条件はテスト可能に。** `tester` がテストに落とせる粒度で書く。
- **データ取得（microCMS）と表示（Astro コンポーネント）を分離**できる設計で記述する。
- 静的ホスティング（Xserver）で成立すること。既存 URL との互換・リダイレクト要否に触れる。
- データ構造は「案」とし、過度に実装を縛らない。
- 未決事項・要決定はまとめて列挙し、独断でスコープを広げない。
