# テスト・レビュー方針（quality）

`tester` と `code-reviewer` が共通の物差しで動くための方針。機能仕様の「受け入れ条件」を
品質判定の一次ソースとする。

## テスト方針
- **純粋ロジックのテストを主軸**にする（Vitest）。対象例: microCMS レスポンス → ドメイン型の変換、
  並び順・件数制限、カテゴリ絞り込み、URL/slug 生成。
- 型・ビルドの健全性は `astro check` と `npm run build` で必ず確認する。
- 表示・統合は補助的に検証する（ビルド成果物のリンク切れ確認、必要に応じ Playwright でのスモークテスト）。
- microCMS API はテストで呼ばず、フィクスチャ（JSON）とモックで再現可能にする。
- 受け入れ条件を 1 つずつテストケースに対応づける。
- テストは独立・決定論的に保つ（順序依存・時間依存を避ける）。

## レビュー観点
- **正しさ**: 受け入れ条件どおりか。境界・異常系（CMS 0 件、画像・カテゴリ欠落）の考慮。
- **責務分離**: データ取得と表示が分離されているか。
- **可読性/命名**: 周囲のコードと一貫しているか（FLOCSS の `l-` / `c-` / `p-` 接頭辞含む）。
- **将来拡張への素直さ**: 後フェーズの拡張を阻害しないか。
- **過剰な複雑化の回避**: 不要な抽象化・早すぎる最適化をしていないか。
- **セキュリティ**: 秘密情報のハードコード・コミット・ログ出力が無いか。CI/CD の権限・Secrets・rsync 範囲が安全か。
- **Web 品質**: セマンティック HTML、`alt`、メタ/OGP、不要な JS・巨大画像の混入。

## CI での自動チェック（P2 以降）
- PR 時に lint / `astro check` / `npm test` / `npm run build` を実行し、すべて成功をマージ条件とする。

## 運用
- レビューは差分単位で、指摘に**重大度**（重大 / 中 / 軽微・好み）を付け、根拠と修正案を添える。
- 修正の適用・コミットは**承認後**に行う。
- テスト結果はありのまま（失敗はログ付きで）報告する。
